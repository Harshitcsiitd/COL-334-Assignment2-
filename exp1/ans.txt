Experiment 1: Report AnswerQuestion: How does the listening socket differ from the socket representing the connection to the client?
Answer: The Exchange Server owns two structurally different TCP sockets. The listening socket (fd 3) is bound only to the local half of the address (127.0.0.1:5000) with a wildcard foreign address (*:*). It carries no data and instead holds the SYN/accept queues, which is confirmed by netstat -aLn showing backlog counters (0/0/128) rather than Recv-Q/Send-Q byte counters. The connected socket (fd 5) returned by accept() is identified by the complete 4-tuple (127.0.0.1:5000 ↔ 127.0.0.1:26623) and is the only socket over which application bytes can flow.  Approach:
Because the connection is idle and persists indefinitely, this is a static-state experiment. The strategy was to photograph the same two sockets through three independent kernel views to show they agree: netstat for the protocol control block table, sockstat for PCBs joined to processes, and procstat -f for the per-process file-descriptor table.  Observations from Screenshots:Protocol View: netstat shows three rows for port 5000, confirming the server-side listening socket, the server-side connected socket, and the client-side connected socket. Both Recv-Q and Send-Q are 0.  File-Descriptor View: procstat -f proves the server process holds distinct descriptors for the listener (fd 3) and the accepted connection (fd 5).
